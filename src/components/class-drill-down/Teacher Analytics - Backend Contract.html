Teacher Analytics — Backend Contract

Endpoint shapes the analytics dashboard consumes. All routes are authenticated as a teacher and scoped to classes that teacher is assigned to. All identifiers are server-issued. Responses are JSON.

Aggregation strategy. Most endpoints are read-mostly aggregations over BKT mastery snapshots and submission rows. Cache aggressively (5–15 min TTL keyed by {teacherId, classId, termId}). Recompute on submission ingest webhook or BKT update event. Heatmap and trend endpoints should support If-None-Match with ETags.

3. Student roster (drill level 2)

GET/api/teacher/classes/:classId/students

Roster with per-student aggregates. Server should support ?sort=overall&dir=desc&filter=at-risk&q=tina to keep large rosters cheap.

{
  "students": [
    {
      "id": "s-4A-01", "name": "Tinashe Moyo", "avatar": "TM",
      "overall": 0.71,        // avg BKT mastery across all skills
      "velocity": 0.018,      // avg weekly mastery delta, signed
      "avgScore": 68,         // avg submission score (0-100)
      "submissions": 14, "onTime": 12,
      "lastActiveDays": 2,
      "atRisk": false, "excelling": true,
      "flagged": false      // teacher's own intervention flag
    }
  ],
  "counts": { "all": 32, "atRisk": 7, "excelling": 9, "flagged": 3 }
}

"At risk" classification rule

Server-side function — keep this consistent across all endpoints:

  • overall < 0.45, OR
  • Negative velocity on ≥ 4 skills over the last 4 weeks, OR
  • lastActiveDays > 9 during an active term

5. Actions (writes)

POST/api/teacher/students/:studentId/flag

Toggle the teacher's intervention flag on a student.

// Request
{ "flagged": true, "reason": "Mastery declining 4 weeks running" }

// Response: 200 OK, returns updated student aggregate
POST/api/teacher/practice-assignments

Create a targeted practice assignment on a weak skill. Backend should generate a problem set from the skill bank.

// Request
{ "studentIds": ["s-4A-01"],     // or "*" for whole class
  "skillIds": ["alg-quad"],
  "itemCount": 10,
  "dueAt": "2025-12-15T17:00:00Z",
  "source": "weakest-skill" }       // or "misconception:mc-001"

// Response: 201 Created
{ "assignmentId": "pa-2031", "itemIds": ["i-…"], "deepLink": "…" }
POST/api/teacher/messages

Send a message to a student or guardian. Reuses your existing announcements/messaging service.

{ "to": { "studentId": "s-4A-01", "channel": "guardian-sms" },
  "subject": "Performance check-in", "body": "…",
  "context": { "skillId": "alg-quad", "mastery": 0.32 } }
GET/api/teacher/classes/:classId/report.pdf

Server-rendered PDF of the class overview. Same shape as /overview but rendered with your existing report templates. ?format=csv for the roster table.

7. New tables / views to add

  • misconception_clusters — id, skill_id, label, signature_pattern, severity, example_question, common_wrong_answer, last_seen_at
  • misconception_assignments — joins (cluster_id, submission_id, student_id) for traceability
  • analytics_class_daily — denormalized daily snapshot: class_id, term_id, day, avg_mastery, at_risk_count, excelling_count, ...
  • analytics_school_daily — same shape, school-scoped, for benchmarks
  • teacher_student_flags — teacher_id, student_id, reason, created_at, resolved_at
  • v_student_risk — view applying the at-risk classification rule

8. Realtime / freshness

The dashboard shows mastery numbers that should feel live but tolerate ~5 min staleness. Recommended approach:

  • BKT updates fire bkt.updated events → invalidate per-student cache
  • Submission ingest fires submission.graded → invalidate class-overview cache
  • Nightly cron computes analytics_*_daily for trend endpoints
  • Heatmap is read-once-per-page-load; no need for websocket push

9. Authorisation

  • All :classId routes: assert teacher_classes.teacher_id = current_user.id AND class_id = :classId
  • All :studentId routes: assert the student is in a class the teacher owns
  • Guardian contact details require teacher.can_message_guardians = true
