01

System architecture

Four moving parts. The phone is a thin capture client; the web is the orchestration surface; the API broker pairs them; the OCR worker is async.

The transport rule

Phone never talks to the web app directly. Both connect to the same broker, joined by a session ID. The broker fan-outs WS events to whoever has joined that session.

Why signed URLs

Image bytes never pass through your API. Phone uploads directly to object storage with a 5-min signed URL. Cheap, fast on flaky networks, scales linearly with storage.

Why async OCR

A vision-LLM call is 3–8s per page. You cannot block the request. Queue it, return a job ID, push the result over WS when ready.

03

Mobile (S21 Ultra) — what to build

It's a PWA. The 8 screens you've mocked map cleanly to routes. Camera, edge detection, and resilient upload are the three non-trivial bits.

Camera capture

Use getUserMedia with facingMode: 'environment' for the back camera. Stream into a <video>, then on shutter press, copy a frame to <canvas> and export JPEG.

const stream = await navigator.mediaDevices.getUserMedia({
  video: {
    facingMode: 'environment',
    width:  { ideal: 3840 },
    height: { ideal: 2160 },
  },
});
videoEl.srcObject = stream;

// On shutter:
canvas.width = video.videoWidth;
canvas.height = video.videoHeight;
canvas.getContext('2d').drawImage(video, 0, 0);
canvas.toBlob(blob => uploadPage(blob), 'image/jpeg', 0.85);

S21 Ultra's main sensor goes up to 108MP but Chrome caps at the requested ideal — 4K is the sweet spot for OCR (file ~500KB at 0.85 quality).

Edge detection (the green outline)

Two practical options:

  • jscanify (~80KB, OpenCV.js wrapper). Detects paper corners every frame, lets you draw the outline. Drop-in.
  • Skip it for MVP. Just show fixed corner brackets and rely on auto-crop server-side. Most teachers shoot reasonably square already.
Recommend: Ship MVP without on-device edge detection. Add jscanify in V1 once you have real shot quality data.

Resilient upload

Africa has spotty connectivity. Build for it:

  • Queue uploads in IndexedDB the moment the shutter fires — UI shows "uploading" optimistically.
  • Service Worker retries with exponential backoff (1s → 2s → 4s → 8s).
  • Upload directly to MinIO with a signed PUT URL. Bypass your API.
  • If teacher closes the tab mid-upload, finish in the SW background fetch.
// IndexedDB outbox pattern
async function enqueuePage(blob, meta) {
  const id = crypto.randomUUID();
  await db.outbox.put({ id, blob, meta, status: 'pending' });
  drainOutbox();  // fire and forget
  return id;
}

Pairing UX

Two paths, both backed by the same /pair endpoint:

  • QR scan — fastest. Use @zxing/browser for the BarcodeDetector fallback. The QR encodes kundai://pair/<sessionToken>.
  • 6-digit code — for when the QR won't focus. Just calls POST /pair/code.

Pair token expires in 60s and is single-use. Once redeemed, phone gets a session JWT scoped to that batch only.

04

Web companion — what to build

This bolts onto your existing teacher dashboard as a new page: /ocr/[batchId]. You're not replacing the upload flow, you're adding a phone-as-source option.

The page lifecycle

  1. Teacher creates a batch (Algebra Quiz · Form 3B) from existing flow → gets a batchId.
  2. Page mounts → calls POST /sessions with batchId → receives sessionId + pairToken + pairCode.
  3. Renders QR of kundai://pair/<pairToken> + the 6-digit code.
  4. Opens WS to /ws/session/<sessionId> and waits.
  5. Phone pairs → WS emits phone:joined → UI flips to "PHONE LIVE".
  6. Phone shoots → each page emits page:uploaded → thumbnail appears in real time.
  7. Phone hits Done per student → emits submission:saved → groups pages under that student.
  8. Teacher hits "Confirm & start OCR" → server enqueues OCR jobs → results stream back via page:ocr_done.

WS client (React hook)

function useOcrSession(sessionId) {
  const [pages, setPages] = useState([]);
  const [phoneLive, setPhoneLive] = useState(false);

  useEffect(() => {
    const ws = new WebSocket(`wss://api.kundai.ac.zw/ws/session/${sessionId}`);
    ws.onmessage = (e) => {
      const ev = JSON.parse(e.data);
      switch (ev.type) {
        case 'phone:joined':    setPhoneLive(true); break;
        case 'page:uploaded':   setPages(p => [...p, ev.page]); break;
        case 'page:ocr_done':   updatePage(ev.pageId, ev.result); break;
      }
    };
    return () => ws.close();
  }, [sessionId]);

  return { pages, phoneLive };
}

Hooking into existing marking

Your dashboard already has a marking surface (see "AI-assisted marking" in the landing copy). The OCR page feeds it:

  • Pages are stored against the existing submissions table.
  • Once OCR returns the structured rubric scoring, it lands in your existing marks table as source: 'ocr_pending_review'.
  • Teacher then opens the normal marking view to confirm/adjust before publishing to students.

Net effect: zero changes to the post-marking flow. The phone is just a new ingress.

Backend contracts

Minimum surface area. Six REST endpoints, six WS event types. Everything else is internal.

WebSocket events · /ws/session/:id

All events are { type, ...payload }. Server broadcasts to every socket joined to that session ID.

EventDirectionPayload
phone:joinedServer → Web{ device, pairedAt }
phone:leftServer → Web{ reason }
student:selectedPhone → Server → Web{ studentId, name }
page:uploadedServer → Web{ pageId, studentId, index, thumbUrl }
submission:savedPhone → Server → Web{ studentId, pageIds, pageCount }
page:ocr_doneWorker → Server → Web{ pageId, transcription, rubricScores, confidence }

Postgres schema (the new tables)

CREATE TABLE ocr_sessions (
  id            uuid PRIMARY KEY,
  batch_id      uuid REFERENCES batches(id),
  teacher_id    uuid REFERENCES users(id),
  pair_token    text UNIQUE,        -- random, expires 60s
  pair_code     text,               -- 6 digits, e.g. '47K92X'
  expires_at    timestamptz,
  phone_paired_at timestamptz,
  status        text                -- pending|live|confirmed|done
);

CREATE TABLE ocr_pages (
  id            uuid PRIMARY KEY,
  session_id    uuid REFERENCES ocr_sessions(id),
  student_id    uuid REFERENCES students(id),
  page_index    int,
  storage_key   text,               -- s3://kundai/.../page.jpg
  uploaded_at   timestamptz,
  ocr_status    text,               -- queued|running|done|failed
  ocr_result    jsonb,              -- transcription + scores
  confidence    float
);
06

OCR + marking pipeline

The actual hard problem. Don't reach for Tesseract — student handwriting (especially mixed math + prose) destroys it. Use a vision LLM with a structured-output prompt.

Why vision LLM, not classical OCR

Tesseract / Document AIVision LLM (Claude/Gemini)
Printed textExcellentExcellent
Neat handwriting40–60% accuracy92–96% accuracy
Scrappy handwriting~20%80–88%
Math notation (x² + 5x)FailsHandles inline LaTeX
Rubric-aware scoringSeparate stepSame call
Cost per page$0.001$0.005–0.02
Latency~500ms3–8s

At Kundai's scale (say 200 schools × 25 teachers × 30 students/quiz × 3 pages × 2 quizzes/week ≈ 900k pages/week), $0.01/page = $9k/week — well within margin if pricing is $0.45–0.85/student/month.

The worker job

# Pseudo-Python — runs in BullMQ consumer
async def process_page(page_id):
    page = await db.get_page(page_id)
    rubric = await db.get_rubric(page.session.batch.assessment_id)

    image_bytes = await storage.get(page.storage_key)

    response = await anthropic.messages.create(
        model="claude-3-5-sonnet-20241022",
        max_tokens=2048,
        messages=[{
            "role": "user",
            "content": [
                {"type": "image", "source": {
                    "type": "base64", "media_type": "image/jpeg",
                    "data": base64(image_bytes)
                }},
                {"type": "text", "text": PROMPT.format(rubric=rubric)}
            ]
        }]
    )

    result = parse_json(response.content[0].text)
    await db.save_ocr_result(page_id, result)
    await ws.broadcast(page.session_id, {
        "type": "page:ocr_done",
        "pageId": page_id,
        "transcription": result["transcription"],
        "rubricScores": result["scores"],
        "confidence": result["confidence"],
    })

The prompt (structure-of)

You are marking a student's handwritten work for the assessment below.

RUBRIC:
{rubric_json}

Return ONLY valid JSON:
{
  "transcription": "",
  "questions": [
    {
      "question_id": "q1",
      "student_answer": "",
      "correct": true | false,
      "marks_awarded": ,
      "marks_available": ,
      "feedback": ""
    }
  ],
  "confidence": <0..1 — how confident you are in the transcription>,
  "needs_review": 
}
Critical: always pair LLM output with a confidence threshold. Anything below 0.85 routes to "needs teacher review" before publishing to the student. Teachers retain final authority — that's both pedagogically right and legally safer.
07

How it fits the teacher's existing workflow

The phone path doesn't replace anything — it's a new way to get paper into the system. After OCR, work flows through your existing marking review screens unchanged.

What stays the same

  • Batch / assessment creation
  • Roster management
  • Rubric / marking scheme editor
  • Mark review & publish to students
  • Analytics dashboards

What's new

  • /ocr/[batchId] page
  • The phone PWA itself
  • Pair token + WS broker
  • Async OCR worker
  • "Needs review" filter on marks list

What this replaces

Nothing, optionally. If teachers currently scan to a flatbed → upload PDF → wait for OCR, the phone path is just faster. Keep the file-upload zone as the fallback (shown in WebOcrCompanion already).

08

Phased rollout

Don't ship all 8 screens day one. Three phases, each independently usable.

Phase 0 · MVP — 3 weeks

Just get paper in

  • Phone screens: Pair, Camera, Done
  • No per-student tagging — bulk upload
  • No live thumbnails — show after Confirm
  • No on-device edge detection
  • OCR runs synchronously on a small queue

Goal: prove the phone-as-scanner path beats whatever they do today (probably WhatsApp).

Phase 1 · V1 — 4 weeks

Realtime + roster

  • All 8 mocked screens
  • Live WS thumbnails on web
  • Per-student tagging on phone
  • OCR worker with BullMQ + Claude vision
  • "Needs review" routing for low-confidence pages

Goal: full happy path from "open phone" to "marks in dashboard" in ≤10 min per class.

Phase 2 · V2 — ongoing

Polish & offline

  • jscanify edge detection + auto-crop
  • Service Worker offline outbox
  • Multi-phone per batch (TA + teacher)
  • Native Android via Capacitor if needed
  • Fine-tuned OCR model on collected data

Goal: works in a rural classroom with one bar of signal.
