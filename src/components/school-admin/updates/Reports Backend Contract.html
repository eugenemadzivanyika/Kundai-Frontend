Reports & Dashboard — Backend Contract

API endpoints the new Reports page and dashboard performance chart depend on. All routes are authenticated as a school admin and scoped to that admin's school.

Conventions: All GET responses are JSON. School ID is inferred from the auth token (req.user.schoolId). All dates are ISO-8601. All percentages are decimals 0–1 unless noted. All IDs are server-issued strings.

1. Dashboard performance chart

Addresses MISS-2. The current getSummary() returns avgClassMastery: 0 hardcoded — replace with a real BKT aggregation.

GET /api/admin/dashboard/performance

Weekly avg BKT mastery for the current term, school-wide and broken down by form.

Query: ?termId=t3-2026&period=term · period ∈ 4w | term | year

// Response 200
{
  "currentMastery": 0.62,           // average of latest mastery snapshot
  "previousTermMastery": 0.54,      // for delta display
  "target": 0.70,                   // from school settings (configurable)
  "weekly": [
    {
      "week": "W1",
      "date": "2026-04-13",
      "schoolAvg": 0.51,
      "byForm": { "F1": 0.48, "F2": 0.50, "F3": 0.55, "F4": 0.52, "F5": 0.49, "F6": 0.54 }
    }
    // ... one entry per week of the requested period
  ]
}

SQL aggregation:

SELECT
  DATE_TRUNC('week', sa.updated_at) AS week,
  sa.form_level AS form,
  AVG(sa.mastery_score) AS avg_mastery
FROM student_attributes sa
JOIN users u ON u.id = sa.student_id
WHERE u.school_id = $1
  AND sa.updated_at BETWEEN $2 AND $3
GROUP BY week, form
ORDER BY week ASC;

4. Generate a report (async job)

Reports can take seconds (school summary) to minutes (term reports for 100+ students). Generate via an async job queue and poll for status.

POST /api/admin/reports/generate 
// Request
{
  "reportTypeId": "term-report",
  "params": {
    "term": "Term 1 2026",
    "classes": ["4A", "4B"],
    "comments": true,
    "mastery": false
  },
  "format": "pdf",           // "pdf" | "excel" | "print"
  "delivery": {
    "mode": "email",        // "download" | "email" | "link"
    "recipients": ["head@…", "parent-form-4a@…"],
    "linkExpiresIn": "7d"    // for mode: "link"
  }
}

// Response 202 Accepted
{
  "jobId": "job-2026-0089",
  "reportId": "r-2026-0089",       // reserved now, accessible once complete
  "status": "queued",
  "estimatedCompleteAt": "2026-05-14T08:48:00Z"
}
GET /api/admin/reports/jobs/:jobId 
{
  "jobId": "job-2026-0089",
  "status": "generating",        // "queued" | "generating" | "ready" | "failed"
  "progress": 0.42,
  "currentStep": "Rendering page 14 of 32",
  "reportId": "r-2026-0089",
  "error": null
}

8. Implementation notes

  • PDF rendering: Use the same Puppeteer / headless Chromium service you'll need for term reports. Each report type ships with a server-side React component that renders to HTML, then to PDF. The preview the user sees in step 3 of the wizard renders the same component client-side with sample data.
  • Concurrency: Cap concurrent generation jobs per school at 3 to prevent one school's term-end batch from blocking another's dashboard refresh.
  • Email delivery: Use the existing announcements/messaging infrastructure. For parent recipients, pull guardian contacts from StudentProfile.guardianEmail. Confirm parent consent flag is set before sending.
  • Share links: Use signed URLs with short token; if requireAuth is true, gate behind the auth middleware and only allow users in the same school.
  • Scheduling: Use a cron-like job runner (Bull, Agenda, or a native interval) that wakes hourly, queries report_schedules WHERE enabled AND next_run_at <= NOW(), generates each, then advances next_run_at per cadence.
  • Caching: The /dashboard/performance endpoint should cache for 15 min keyed by {school_id, period}. Bust on BKT update events.
